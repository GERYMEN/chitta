PHASE R5e — money meaning: card bill payments, ATM withdrawals, wallet
top-ups, own-account transfers, EMI, interest, template refunds.
THIS DISPATCH = CODE + TESTS + GATES ONLY. NO DEVICE WORK (no adb).

WHY: R5d/R5g recognise these SMS (moneyHint 'card_payment' | 'transfer' |
'atm' | 'wallet_load' | 'emi' | 'refund', money_kind 'interest') but only
HOLD them in Pending. Recorded as expenses they double count: a credit-card
bill payment repeats spends already counted on the card; an ATM withdrawal
or wallet top-up only moves the owner's own money.

DECISIONS (orchestrator defaults 2026-11-14, standard money-manager
meaning; the owner may override later):
- M1 card_payment = TRANSFER bank a/c → credit-card account.
- M2 atm = TRANSFER bank a/c → a 'cash' account.
- M3 wallet_load = TRANSFER bank a/c → the wallet account ('other' type,
  institution = wallet, e.g. Paytm / Amazon Pay).
- M4 transfer (own-account NEFT/IMPS/UPI "to self/own a/c") = TRANSFER
  to the owner's other account (user picks when it is not unique).
- M5 emi = EXPENSE, category "EMI & Loans" (new seed `cat-emi`), released
  from the hold (normal approval rules).
- M6 interest = INCOME, category "Interest" (new seed `cat-interest`).
- M7 refund (template money_kind) = INCOME released from the hold, same as
  reader refunds; the R3b refund ranker suggests the linked expense.
- M8 the user confirms a meaning once per (bank canonical, kind,
  counterparty last-4 or institution); a checkbox "Do this automatically
  next time" (default ON) stores a MEANING RULE. Later matches convert
  automatically (still pending in manual approval mode; auto-approved in
  auto mode only when confidence ≥ the threshold).
- Never auto-create accounts, never convert without either a user confirm
  or a stored meaning rule, never touch approved rows without the user.
- No new permission, no new dependency, no network.

PRIVACY (absolute, unchanged): no raw SMS bodies or sender numbers stored
or logged; meaning rules store bank canonical + kind + last-4 or
institution id only (same class of data as account_suggestion_decisions);
audits hold ids/enums only (R3a whitelist sanitizer). Fixtures SYNTHETIC
only (QA names, XX1234/XX9999, refs 000000000xxx, qa.x@okqa).

METHOD for every task: failing test with synthetic input first, confirm it
fails, then fix, confirm it passes.
