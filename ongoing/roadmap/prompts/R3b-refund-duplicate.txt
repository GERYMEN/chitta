TASKS
T1 Refund model (pure, unit-tested):
   - A refund = an income row with link_kind 'refund' and
     linked_transaction_id = the original expense id. It keeps its own
     account, date and status; its category becomes the original's.
   - Totals: a linked refund does NOT count as income. It reduces spend
     (expense total, and per-category sums later) in the period of the
     REFUND's own date. Balance math unchanged (refund money still enters
     the account).
   - Partial and multiple refunds allowed; the sum of refunds linked to
     one expense may not exceed its amount (validate; clear error).
   - Candidate expenses for "Link to original": pure ranker —
     approved/pending expenses, not linked/rejected/transfer, amount ≥
     refund amount minus already-refunded, occurred within 90 days
     BEFORE the refund; rank by same normalizeMerchant key, then same
     account, then closest date. Unit-test ranking + limits.
T2 Duplicate model (pure, unit-tested):
   - findDuplicatePairs(transactions, dismissals, windowMinutes = 10):
     same account, same type (income/expense only), same amount,
     |occurredAt diff| ≤ window, both pending or approved, neither linked/
     transfer/rejected, pair not dismissed. Each row in at most one pair.
     Edge tests: window boundary, 1 paisa off, different account,
     three rows, dismissed.
   - Mark duplicate: the user picks which row to KEEP (default: the
     approved one, else the earlier). The other row becomes status
     'rejected', link_kind 'duplicate', linked_transaction_id = kept id;
     it keeps its sourceReferenceHash (re-sync never recreates it) and is
     hidden from Pending, lists, totals and balances like an R3a twin.
     Store the previous state in the audit metadata (R3a pattern) so
     "Not a duplicate" on the hidden row's detail restores it EXACTLY.
   - "Not duplicates" on a suggestion → dismissal. Migration 7:
     duplicate_pair_dismissals(a_id, b_id, dismissed_at, PRIMARY KEY
     (a_id, b_id)) with a_id < b_id. Parameterized, idempotent.
   - Manual "Mark as duplicate of…" on any pending/approved income or
     expense detail → picker of rows with same account + type + amount
     within 3 days.
T3 Audit (metadata never contains SMS text, merchant text or amounts
   beyond what existing events already store): 'refund_linked'
