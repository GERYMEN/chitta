WHY (review 2026-11-08, orchestrator ran the compiled reader v2 on 30

- Identity: sourceReferenceHash = `sms-<_id>-<date>` (readSms.ts ~468).
  _id is a content-provider row id; a new phone / SMS-backup restore /
  default-SMS-app switch gives new ids → the whole history re-imports

- Reference dedupe is in-run only (syncSms.ts ~284 `seenRefs`); refDigest

  alerts with the same UPI ref arriving in different runs (auto-read vs
  manual) both insert. refDigest is FNV-1a 32-bit: too weak to use as a
  persisted identity (birthday collisions at ~10^4 refs would DROP a
  real transaction).
- Accounts: matching is exact type + last-4 only. A debit card spend
  carries the CARD's last-4 (≠ account's), ICICI masks accounts with 3
  digits ("Acct XX888" → lastFour null → never matches), SBI long masks
  ("A/C XXXXX123456") → lastFour null.
- Parser money errors: (1) "Rs X debited on <d> for UPI Ref N has been
  reversed to your A/c XX1234" → EXPENSE (should be refund); (2) "Rs X
  debited from A/c XX1234 … towards <bank> Credit Card XX9999 payment"
  → accountKind credit_card + lastFour 1234 (bank digits with card
  kind = matches nothing, fake "new credit card 1234"); (3) "Rs X added
  to your Paytm Wallet from HDFC Bank A/c XX1234" → INCOME on HDFC 1234
  (the SOURCE account gets credited; HDFC nets to 0).

T1 Stable SMS identity:
   - smsContentHash = hex(SHA-256(salt + ":" + DLT header ID (or
     "<NUMBER>") + ":" + floor(date/1000) + ":" + normalizedBody))
     truncated to 32 hex chars. Pure-TS SHA-256 (no dependency) with a
     test against published SHA-256 vectors. normalizedBody = the same
     whitespace collapse readSms uses (NOT the footer cut — identity is
     of the whole message).
   - Salt (O1): 32 random bytes from the existing native module (add a
     tiny `randomBytes(n)` to BackupModule.kt using SecureRandom — no new
     module, no permission), generated once, settings key
     `sms_identity_salt`, included in backup, restored before any sync.
   - New column transactions.sms_content_hash (TEXT, nullable) + index.
     The R5-fix tombstone table gets the same column.
   - Dedupe = skip a candidate when EITHER its sourceReferenceHash OR its
     smsContentHash exists on any row (any status) or tombstone.
     sourceReferenceHash format is UNCHANGED (old rows keep deduping).
   - Lazy backfill: when a sync sees a candidate whose old key matches a
     row that has no content hash, write the hash to that row (no audit
     row, no other field changes). Same for tombstones.
   - Tests: same SMS with a different _id dedupes; same body+date from a
     different sender does not; restore-on-new-phone simulation (rows +
     salt restored, ids changed) imports 0 new items.

T2 Persisted reference dedupe:
   - New column transactions.ref_digest (TEXT, nullable) + index; value =
     SHA-256(salt + ":" + upper(ref)) truncated to 32 hex. Replace the
     FNV refDigest everywhere it is used (the in-run guard too).
   - At insert: if a live or rejected row (or tombstone) has the same
     ref_digest AND type AND amount → skip (counted as skipped). A
     reversal (income) never collides with its debit (type differs).
   - duplicate.rules.ts: a pair with equal ref_digest + type + amount is
     a duplicate suggestion regardless of DUPLICATE_WINDOW_MINUTES and
     account (still a suggestion — user confirms; dismissals respected).
   - Refund ranker (R3b): an income with the same ref_digest as an
     expense ranks that expense first.
   - Backup: both new columns included; completeness test updated.
