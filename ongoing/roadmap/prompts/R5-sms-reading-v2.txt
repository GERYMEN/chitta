T1 Parser v2 (pure TS, src/features/sms-sync/parser/ or similar; keep
   parseSmsMessage(msg) as the entry point used by sync; bump a
   PARSER_VERSION constant):
   a) Sender stage: parse DLT headers ("XX-ABCDEF", "XX-ABCDEF-S/T/P/G",
      6-char IDs, plain 10-digit numbers). Drop "-P" (promotional) and
      plain personal numbers / short codes that are not financial.
      Financial sender table: bank/card/wallet/paylater header IDs →
      canonical institution (extend normalizeAccountKey aliases; keep
      its version constant consistent, bump if behaviour changes).
      Unknown senders are NOT dropped outright — they go through the
      classifier with a lower prior (friend's bank may be unknown).
   b) Classifier: label each message one of txn_debit, txn_credit,
      card_spend, refund/reversal, failed/declined, otp, mandate_future
      ("will be debited", "e-mandate", "autopay scheduled"),
      collect_request ("has requested", "request money"), bill_due /
      statement ("due on", "min amount due", "statement generated"),
      loan_or_promo ("pre-approved", "eligible", "limit increased",
      "apply now"), balance_info, unknown_financial, not_financial.
      Replace the blanket reject words with these targeted classes —
      "Avail Bal"/"Avl Bal"/"available balance" must NOT reject.
      Decide debit vs credit from the verb NEAREST the transaction
      amount / the account phrase ("A/c XX1234 credited", "debited from
      A/c", "Dr"/"Cr", "sent", "transferred", "withdrawn", "purchase",
      "spent on card", "received from", "deposited"), not from any word
      anywhere.
      Only txn_debit, txn_credit, card_spend, refund produce
      transactions. bill_due/statement are returned as typed non-
      transactions (R5b will use them) — not inserted now.
   c) Extraction: transaction amount = the amount bound to the
      transaction verb (with or without Rs/INR/₹/Rs./INR. prefix,
      Indian digit grouping 1,00,000.00, decimals optional); ignore
      amounts after Avl/Avail/Available Bal/Balance/limit/credit limit/
      min due. Account last-4 (XX1234, X1234, *1234, ending 1234, A/c
      no. XXXXXX1234, card ending). Payee/merchant: UPI "to VPA" / "trf
      to NAME", "at MERCHANT", "from NAME/VPA" for credits, "Info:" /
      "NEFT-…-NAME" tails, card "at MERCHANT on". UPI/IMPS/NEFT ref
      (kept only as part of the dedupe hash input, never shown/stored
      raw — hash it). Transaction date: SMS date (keep), body date only
      if you can make it robust (optional, document).
   d) Salary: tag txn_credit as salary when the body has SAL/SALARY/
      PAYROLL/"salary credit" tokens (word-bounded; NEFT tails like
      "NEFT-…-SALARY OCT"); set category to the existing Salary
      category if one exists (find it in the seed categories); mark
      confidence high. Recurring-pattern salary detection is out of
      scope (R8).
   e) Confidence: recompute from signals (known sender, clear verb,
      bound amount, account found, merchant found). Integer amounts are
      not penalised by themselves.
   f) Institutions with templates + synthetic fixtures (≥3 fixtures each
      where formats differ: debit UPI, credit, card/ATM): SBI, HDFC,
      ICICI, Axis, Kotak, Federal, PNB, Bank of Baroda, Canara, Union,
      Bank of India, Indian Bank, IOB, Central Bank, IDFC First, Yes,
      IndusInd, South Indian Bank, CSB, Kerala Gramin, AU, RBL, Bandhan,
      DBS, Paytm Payments Bank, Airtel Payments Bank, Fi/Jupiter
      (Federal-based); cards SBI Card, HDFC/ICICI/Axis cards, Amex,
      OneCard; wallets Amazon Pay, Paytm. Plus a GENERIC path for
      unknown banks that handles the common shapes. Negative fixtures:
      OTP, promo/loan offer, mandate_future, collect_request, failed,
      bill_due, balance_info.
   g) Tests: table-driven fixture suite (type, amount, last-4, payee,
      salary, class) + a regression set of the v1 bugs above + property
      checks (no output field contains the raw body/sender; amount
      never equals the balance figure in fixtures that have both).

   - Run the existing incremental sync (R4b window, cursor, overlap,
     dedupe, pair holds, auto-approve rule) a few seconds after the
     broadcast (inbox write lands after the broadcast). App in
     foreground: native event → JS runs sync (respect the existing
     single-flight guard; coalesce bursts). App in background/killed:
     RN Headless JS task (HeadlessJsTaskService, part of RN core — not a
     new dependency) running the same sync code with a short timeout;
     no UI. Document Android 8+/12+ background-start behaviour you rely
     on (SMS_RECEIVED temp allowlist).
   - Skip when onboarding not completed, permission missing, or the
