PART A — Backup / restore
A1 Native (own Kotlin module, e.g. BackupModule; SmsReaderModule /
   FeedbackModule pattern; register in MainApplication):
   - saveBackup(json, password, suggestedName): Storage Access Framework
     ACTION_CREATE_DOCUMENT (no permission; user picks Downloads, Drive,
     etc.), encrypt, write to the chosen URI. Resolve
     {saved: true, name, bytes} or {saved: false} when cancelled.
   - openBackup(password): ACTION_OPEN_DOCUMENT, read, decrypt, resolve
     the JSON string; distinct reject codes: E_CANCELLED, E_NOT_BACKUP
     (bad magic/format), E_BAD_PASSWORD (GCM tag fail — same message for
     damaged file: "Wrong password or damaged file"), E_TOO_NEW (format
     version newer than this app).
     (If two-step is cleaner — pick file, then ask password, then decrypt
     — do that: pickBackup() returns a handle/uri, decryptBackup(uri,
     password); document.)
   - Crypto (javax.crypto only): PBKDF2WithHmacSHA256, random 16-byte
     salt, ≥210,000 iterations (store the count in the header),
     AES-256-GCM, random 12-byte IV, 128-bit tag. File = magic
     "TRKBK" + format version byte + iterations + salt + IV + ciphertext.
     Run crypto + IO off the UI thread. Never log the password, JSON,
     key or file contents; zero the password char array after use.
   - If JVM unit tests are already wired (android/app/src/test + junit on
     the test classpath), add a crypto round-trip + wrong-password test;
     otherwise extract the crypto into a small pure Kotlin object and
     document that it is untested on JVM.
A2 JS backup payload (pure, zod-validated):
   {format: 1, app: {versionName, versionCode}, schemaVersion (current DB
   migration number), createdAt ISO, tables: {<name>: rows[]}} — every
   user-data table (accounts, transactions, categories, settings,
   audit/activity, links, duplicate_pair_dismissals, sms_sync_runs, any
   others — enumerate from schema/migrations; list them in the report).
   Raw SMS bodies are never stored, so none are exported (only what the
   DB already holds). Read via the repositories / one read transaction.
A3 Restore (replace everything):
   - Validate payload; refuse schemaVersion > current ("Backup is from a
     newer app — update Tracker first"). Older schemaVersion: load into
     the schema of that version then run migrations forward, OR document
     a mapping approach — must be correct and tested for at least
     version N-1 → N.
   - ONE DB transaction: delete all user-data rows, insert backup rows;
     any failure rolls back fully (app data unchanged).
   - After success: audit row 'backup_restored' (counts per table only),
     reload every store (accounts, transactions, settings, tour,
     feedback widget position, sync start/cursor) so the UI reflects the
     restore without an app restart; navigate to Home.
   - Restored data from another phone: keep sms sync settings as backed
     up (document; dedup by sourceReferenceHash prevents doubles).
A4 UI:
   - Settings sheet: "Back up data" → screen/sheet: password + confirm
     (min 8 chars, show/hide, strength hint not required), warning
     "If you forget this password the backup can't be opened", [Save
     backup file] → SAF → Snackbar "Backup saved".
     Default file name tracker-backup-YYYY-MM-DD.trkbak.
   - Settings sheet: "Restore from backup" → pick file → password →
     confirm Dialog "Replace all data in Tracker with this backup
     (<date>, N transactions, M accounts)?" → restore → Snackbar
     "Backup restored".
   - Onboarding first screen: "Restore from a backup" link (new phone /
     reinstall). After a successful restore, onboarding completes (the
     backup carries onboarding/profile settings) and the tour is NOT
     shown if the backup has tour_completed_at.
   - Show the last backup date under "Back up data" (settings key
     last_backup_at; device-local, not restored over — document).
   - ≥48dp, accessibility labels, password fields secureTextEntry,
     no autofill of the password into logs.
A5 Tests: payload round-trip (export → restore → identical rows for
   every table); validation errors (bad format, newer schema, missing
   table); restore rollback on mid-way failure; older-schema restore;
   store reload after restore; onboarding restore path skips tour;
   password rules (min length, confirm match); no password/JSON in
   console/audit.
