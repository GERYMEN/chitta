DEFAULTS (orchestrator; owner may override later):
D-a Persist chain suggestions in a NEW table `chain_suggestions` (new numbered
    migration 12, never edit old ones): id TEXT PK, kind TEXT NOT NULL
    ('duplicate' | 'refund_link' | 'transfer_twin' | 'incomplete'),
    child_id TEXT NOT NULL, parent_id TEXT (nullable), parent_override TEXT
    (nullable; JSON of ENUM/BOOLEAN fields of RuleChainOverride ONLY —
    deleted, link, incomplete — never any free text or SMS body),
    status TEXT NOT NULL ('open' | 'accepted' | 'dismissed' | 'superseded'),
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL. Index on
    (status, child_id). One row per child_id (a newer suggestion for the same
    child REPLACES the open one). Backup/restore (R4e) includes the table;
    restore of an old backup without the table still works.
D-b Replace the session-only useChainSuggestions with a repository-backed
    store (new src/data/repositories/chainSuggestion.repository.ts +
    src/features/review/state or feature store), keeping the same call sites
    in syncSms.ts working (add on resolve, remove on completion). Writing a
    suggestion persists an 'open' row; completing a parent / confirming /
    dismissing updates status. Suggestions survive restart.
D-c Chain suggestions NEVER touch balances and NEVER create a transaction on
    their own. They only surface a pending child + its proposed link; the
    link is applied only when the user Accepts.
D-d De-dupe against existing Review sections: a chain suggestion whose child is
    ALREADY surfaced by useTransferPairs (transfer_twin) or useDuplicatePairs
    (duplicate) must NOT appear twice. Policy: the Review "Linked by rules"
    section shows only chain kinds with NO existing UI — refund_link and
    incomplete — plus any duplicate/transfer_twin chain whose child is not
    already in the transfer/duplicate sections. Document which kinds you
    surfaced and why in the report.
D-e Review "Linked by rules" section (new component, ReviewSections.tsx):
    each row shows the child (payee/account/date/amount via existing masked
    rule), the proposed relation (Refund of … / Part of a transfer / Looks
    like a repeat / Waiting for the matching alert), and actions:
    - refund_link: Accept -> link as refund (reuse the existing refund link
      store action), Dismiss.
    - transfer_twin: Accept -> confirm as transfer (reuse confirmTransferPair
      semantics), Dismiss.
    - duplicate: Accept -> mark duplicate (reuse markDuplicate), Dismiss.
    - incomplete: no Accept (nothing to link yet) — show "Waiting for the
      matching alert", Dismiss only.
    Accept RE-CHECKS at tap time: child + parent still exist, still
    pending/approved, not already linked, not changed. On a stale/superseded
    pair the store action returns ok=false -> set the row status 'superseded'
    + snackbar "This pair changed — not recorded" (match existing copy).
    Dismiss sets status 'dismissed' with a 5 s Undo (reuse the shared
    Snackbar). >=48 dp targets, a11y labels/roles.
D-f 'failed' SMS: money did NOT move -> never a transaction, never a bill,
    never a suggestion, and never shown in "Messages not understood" (it is
    understood). Keep today's drop behaviour; lock it with tests. No UI.
D-g 'collect_request' SMS: a request to pay, not money moved -> same as D-f
    (dropped, tests, no UI). Note in the report that surfacing collect
    requests as reminders is a possible future owner option, not built here.
D-h Multi-record (ATM withdrawal + fee, one SMS -> 2 records via template
    reparse) is already supported. VERIFY with a synthetic test that a
    template emitting 2 transaction records yields 2 pending rows with
    distinct per-record content hashes and correct amounts. If no rules.json
    route produces an ATM-withdrawal-plus-fee pair, ADD the pattern to the
    rules DATA via scripts/rules (build_rules.js + validate_v2, synthetic
    samples + negatives) — do NOT hand-edit the generated rules.json.
D-i Audit: chain_suggested / chain_accepted / chain_dismissed (ids + enum
    kind only, no amounts beyond the existing masked rule) shown in Activity.
