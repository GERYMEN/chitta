REQUIREMENTS (from D9 + the answered open question):

- Periods: `'1M' | '3M' | '6M' | '9M' | '1Y'`. NO calendar-year picker this
  phase (the skill's SKILL.md mentions one as a maybe; the user has not
  asked for it and D9's open question about calendar-year semantics was
  answered as "not needed for v1" — trailing-12-months only).
- `1M` (default) = the 1st of the CURRENT calendar month, at local
  midnight, through `now` (the moment the function is called, or the
  explicit `now` parameter in tests).
- `3M` = the 1st of the month TWO months back from the current month
  (i.e. "current + 2 previous full months"), at local midnight, through
  `now`. Example: if today is March 15th, 3M starts January 1st.
- `6M`/`9M` follow the same pattern (current + 5 / current + 8 previous
  full months respectively), 1st of that starting month at local midnight
  through `now`.
- `1Y` = TRAILING 12 months — this is the one place this period does NOT
  follow the "1st of some month" pattern the others use. Per the answered
  open question, "1Y" means the rolling window exactly 12 months back from
  `now` (i.e. `now` minus 12 months, same day-of-month, at local
  midnight), NOT the 1st of a month 11 months back, and NOT Jan 1 of the
  current year. Implement it as `now` minus exactly 12 calendar months
  (handle month-length differences correctly — e.g. if `now` is March 31,
  12 months back should sensibly resolve to the previous March, clamping
  to that month's last valid day if it doesn't have a 31st — document
  your exact clamping behavior in the output report since this is a real
  edge case the acceptance criteria call out).
- Signature: `periodRange(period: Period, now: Date, timeZone?: string):
  { from: Date; to: Date }` (or equivalent — your call on exact types, but
  it must take an explicit `now` so it's fully testable without mocking
  the system clock, and the result's `to` is simply the `now` passed in,
  not re-derived). Keep it a pure function — no I/O, no `Date.now()`
  called internally.
- "One pure `periodRange(period, now, timezone)` at local midnight,
  unit-tested at month ends, leap years, year boundaries" — the
  "timezone" parameter: this app has no explicit timezone-selection
  feature anywhere, and `Date` in RN/JS is inherently local-device-timezone
  already. Accept an optional `timeZone` parameter for forward
  compatibility (the skill explicitly names it), but if there's no existing
  timezone-handling utility anywhere in this codebase to lean on, it's
  acceptable to leave it unused/document it as a no-op placeholder for a
  future phase, rather than pulling in a new date-timezone library — note
  this honestly in your report, don't silently drop the parameter without
  saying so, and don't add a new npm dependency to implement full IANA
  timezone support that nothing else in this app uses yet.
