CONTEXT: the user reviewed real Sync SMS results on their device and gave
concrete, specific feedback (their own screenshots, which the orchestrator
has already seen and translated into generic requirements below — you do
NOT need to see or reproduce any of the user's actual message content,
everything you need is already generalized here):

1. Real bank/UPI transaction SMS always carry a bank name and a 4-digit
   account or card number embedded in the message (e.g. "...from a/c X1859
   ... -Federal Bank", "...From HDFC Bank A/C *7302...", "...HDFC Bank card
   ending 8123..."). The CURRENT parser (Phase 4) ignores this entirely —
   `resolveAccountIdForSms` in `src/features/sms-sync/smsSyncLogic.ts` only
   checks if an EXISTING account's `lastFour` happens to appear in the
   body, and if nothing matches, silently falls back to `accounts[0]`. This
   is wrong: it can silently misattribute a transaction to the wrong
   account.
2. A credit card number and a bank account number are DIFFERENT kinds of
   account even if the 4 digits were ever coincidentally similar — the
   parser must distinguish `credit_card` from `bank` from `upi` (the
   existing `AccountType` already has `'credit_card'` as a distinct value
   from `'bank'`/`'upi'`, per `src/domain/accounts/account.types.ts` — this
   phase is about actually USING that distinction during SMS matching,
   which Phase 4 never did).
3. When a message's extracted (bank name + account kind + last-4) doesn't
   match any EXISTING account by BOTH `lastFour` AND `type` (not lastFour
   alone), the app must NOT silently fall back to the first account. It
   must instead SUGGEST a new account to the user and let them approve
   creating it before any transaction from that account/card is recorded —
   same "Detect→Review→Approve→Record" principle this whole app already
   applies to transactions, just extended one level up to accounts
   discovered via SMS.

ADDITIONAL GROUND FACTS (verified, exact current state):

- `src/features/sms-sync/smsParser.ts`'s `ParsedSmsTransaction` type
  (Phase 4) currently has: `type, amountMinor, merchantName, occurredAt,
  confidenceScore, sanitizedPreview, sourceReferenceHash`. Extend it with:
  `bankName: string`, `accountKind: AccountType` (reuse the existing
  `AccountType` from `src/domain/accounts/account.types.ts` —
  `'bank'|'cash'|'credit_card'|'upi'|'other'`; a parsed SMS will only ever
  produce `'bank'|'credit_card'|'upi'`, never `'cash'`/`'other'`), and
  `lastFour: string | null` (4 digits, or null if truly unextractable —
  treat an unextractable last-four as its own "unknown" bucket rather than
  dropping the message, see T2).
- Heuristic extraction (keep it genuinely simple regex, document your exact
  patterns in the output report):
  - `lastFour`: a pattern looking for 4 digits near an account/card
    keyword, e.g.
    `/(?:a\/?c|acct|account|card)[^\d]{0,20}(?:ending\s*)?[x*]{0,6}\s*(\d{4})\b/i`
    — adjust as needed for robustness, test against varied synthetic
    formats (see T4's test fixtures), but the core idea is: find a 4-digit
    number that appears near the words "a/c", "account", or "card" (not
    just any 4-digit number anywhere, which would false-match reference
    numbers or balances).
  - `accountKind`: `'credit_card'` if the body matches
    `/credit\s*card|card\s+ending|\bcc\b/i`; else `'bank'` if it matches
    `/\ba\/?c\b|\baccount\b|bank\s+a\/?c/i`; else `'upi'` as the default
    fallback for a clear UPI transfer message with no bank/card wording at
    all. Check `credit_card` before `bank` (a credit-card message may also
    contain the word "account" loosely, card wording should win).
  - `bankName`: look for a capitalized word immediately before the literal
    word "Bank" (e.g. `/([A-Z][A-Za-z]+)\s+Bank\b/` capturing "HDFC",
    "Federal", "SBI" if it appears as "SBI Bank", etc.) OR a trailing
    signature pattern like `/-\s*([A-Za-z ]+Bank)\s*$/` at the message's
    end. If nothing matches, use the literal string `'Unknown Bank'` — this
    is a best-effort v1 heuristic, document its real limitations honestly
    in your report (it does not use a lookup table of known bank names,
    and the user will sometimes have to rename an auto-suggested account).
- `resolveAccountIdForSms` (`smsSyncLogic.ts`) must be rewritten: given
  `accounts: Account[]` and a parsed candidate's `{ bankName, accountKind,
  lastFour }`, return the matching account's `id` ONLY if an existing
  account has BOTH `account.type === accountKind` AND (`lastFour != null &&
  account.lastFour === lastFour`). If no such match exists, return `null`
  (NOT `accounts[0]` — remove that fallback entirely, it's the bug this
  phase fixes). A `null` result means "needs a suggested account", handled
  by T2/T3, NOT "assign to some arbitrary account".
- `syncSms()` (`src/features/sms-sync/syncSms.ts`) currently creates a
  transaction for every parsed, non-duplicate candidate. Change it so that
  candidates whose `resolveAccountIdForSms` returns `null` are NOT turned
  into transactions this run — they're grouped into suggestions instead
  (T2). Candidates that DO match an existing account behave exactly as
  Phase 4 (unchanged).
- `src/app/navigation/routes.ts`/`RootNavigator.tsx`: add a new route
  `SmsSuggestions: { suggestions: SmsAccountSuggestion[] }` (a plain
  serializable array, fine as nav params — keep `SmsAccountSuggestion`'s
  shape small: `{ bankName: string; accountKind: AccountType; lastFour:
  string | null; messageCount: number }`, no SMS content in it). Also
  extend `AddAccount`'s params from `undefined` to `{ prefill?: { name:
  string; type: AccountType; lastFour: string | null } } | undefined` (stays
  backward compatible — existing `navigation.navigate('AddAccount')` calls
  with no params remain valid since the field is optional) so the
  suggestions screen can deep-link into a pre-filled Add Account form
  instead of a blank one.
- `src/features/accounts/screens/AddAccountScreen.tsx` (Phase 3) already
  renders `<AccountForm initialValues={...} .../>` — Phase 3's version
  passes no `initialValues` (blank form). Read the route params'
  `prefill` (if present) and map it into `AccountForm`'s
  `initialValues` (`name`, `type`, `lastFour` — `openingBalance` stays
  default `"0"`, the user fills in a real opening balance themselves, SMS
  data never tells you an opening balance).
