=== HARD RULES (violating any one = stop the run and report) ===
These are not new — they are this session's accumulated, hard-won rules
after three real incidents (documented in STATE.md's decisions log: a
real Messages-app visit + dump, a real merchant/amount leaked via an
unfiltered screen dump, and a direct sqlite3/adb manipulation of
tracker.db). Follow them exactly, no exceptions, no "just this once":

1. App isolation: interact ONLY with com.tracker, plus the system permission
   dialog when it is expected. Before EVERY tap, run:
     adb shell dumpsys activity activities | grep topResumedActivity
   If anything other than com.tracker/.MainActivity (or the expected
   permission dialog) is in front, press back/home to return to Tracker.
   Do NOT inspect, dump, or read anything from the other app.
2. No personal data in output: never log, print, write to a file, or quote
   SMS bodies, sender numbers, merchant names, or amounts that came from
   real SMS. SMS checks are COUNT-ONLY (e.g. "created=29", "badge=4"). The
   one established exception: bank name / account type / last-four digits
   ARE safe to report (same category of info already shown on the user's
   own Accounts screen for their own accounts) — but never merchant/amount/
   sender from a real message.
3. uiautomator dumps on Home, Pending, Transactions, Transaction Detail,
   Accounts, or Suggestions must be filtered to the single element you are
   locating, e.g.:
     adb shell uiautomator dump /sdcard/u.xml && adb shell cat /sdcard/u.xml \
       | grep -o 'text="Sync SMS"[^>]*bounds="[^"]*"'
   Never print a full dump. Delete /sdcard/u.xml afterward.
4. No screenshots unless topResumedActivity confirms Tracker is focused AND
   text evidence (logcat / filtered dump) is genuinely insufficient. Prefer
   text.
5. NEVER read, write, push, pull, or run sqlite3 / run-as against
   tracker.db or any file under the app's data dirs, for ANY reason. If
   data is empty, create what you need through the app's own screens (Add
   Account, Add Record) with real taps. (A prior phase violated exactly
   this rule to seed test accounts — do not repeat that.)
6. Use only synthetic data you type yourself, e.g. account "QA Test Bank
   0001" and merchant "QA-Merchant-01". Never use real names.
7. Do not uninstall the app or clear its data unless a test below
   explicitly says so. Those tests run LAST, in section F, and are marked
   NOT RUN by default in this dispatch (not pre-approved — see section F).

=== SPECIFIC KNOWN ISSUES TO INVESTIGATE (user-reported, this session) ===
The user reviewed their real Accounts screen after Phase 8's test and found
two concrete problems. Both are already partially explained by Phase 8's own
report but need independent QA verification and root-cause documentation —
do not just accept the existing explanation, verify it:

K1. **Duplicate accounts**: the Accounts screen shows TWO separate "HDFC
    •••• 0197" Credit Card entries, both ₹0.00. Phase 8's report
    (08-full-workflow-verification.md, "Test-hygiene note" section)
    explains this as its OWN testing artifact — it says fast swipe
    gestures accidentally triggered the Add Account flow multiple times
    during its own investigation, creating duplicates including "HDFC
    credit 0197 ×2". Verify this explanation is complete and correct, AND
    separately test whether the APP ITSELF has any safeguard against a
    user (or the SMS suggestion flow) creating two accounts with identical
    (type, bankName-derived name, lastFour) — currently there is no
    uniqueness constraint in the schema or the Add Account form. Try
    deliberately creating two accounts with the same name/type/lastFour
    via the normal UI and confirm whether the app warns, blocks, or
    silently allows it. If it silently allows it, document this as a real
    product gap (not a crash, but a data-quality issue worth a bug entry)
    with severity S3 (wrong display / confusing data) — recommend (don't
    implement) a duplicate-detection check in the Add Account form as a
    follow-up.
K2. **Missing/mislabeled bank**: the user's real inbox has genuine State
    Bank of India (SBI) messages, but the SMS Suggestions screen has never
    shown a group labeled "SBI" or "State Bank of India" — instead one
    suggestion group shows as "Unknown Bank" for what the user believes is
    an SBI-sourced transaction. Investigate `src/features/sms-sync/
    smsParser.ts`'s `bankName` extraction regex (documented in
    07-sms-account-matching.md): it currently looks for a capitalized word
    immediately before the literal word "Bank" (`/([A-Z][A-Za-z]+)\s+Bank\b/`)
    or a trailing `"- X Bank"` signature. Hypothesize and verify (using
    ONLY fabricated synthetic test strings you write yourself, e.g. `'Rs.500
    debited from SBI Card ending 5368 at QA-Merchant'` or similar patterns
    that plausibly resemble how an SBI message might phrase it without the
    literal word "Bank" adjacent to "SBI") whether a message that says
    "SBI Card" or "SBI A/C" (without the word "Bank" right next to "SBI")
    fails to extract "SBI" as the bankName and falls through to
    'Unknown Bank'. Write this up as a parser bug (do NOT fix it) — this
    is a real accuracy gap in the v1 heuristic that the existing phase
    reports already flagged as a known limitation ("no bank-name lookup
    table"), but the user has now confirmed it's materially wrong for a
    real case, which is useful, concrete confirmation worth its own bug
    entry.

=== TEST PLAN ===
For each test, record: ID, area, steps, expected, actual, status
(PASS/FAIL/BLOCKED/NOT RUN), evidence level, severity (S1 crash/data loss,
S2 broken flow, S3 wrong display, S4 cosmetic).

Evidence levels (do not inflate): built | installed | launched |
journey-verified. Debug-build results are NOT release-build results.

A. Static gates (run first)
- npx tsc --noEmit -p tsconfig.json
- npx eslint src --ext .ts,.tsx
- npx jest (record test count)
- cd android && ./gradlew assembleDebug
- cd android && ./gradlew assembleRelease. If signing is not configured,
  record BLOCKED with the reason. Do not configure signing.

B. Critical journeys (journey-verified on device)
- B1: Add Account from the Accounts screen; B2: from "Add New Money
  Source". Each must appear in the Add Record account picker.
- B3: Add Record → appears in Pending → Approve → appears in Transactions.
  Account balance = opening + approved income − approved expense.
- B4: Edit an approved record (merchant, amount, category). The change
  persists and the balance recalculates.
- B5: Delete a record (if supported — check whether this exists at all;
  if not, record NOT RUN with "no delete feature built this session").
- B6: Reject or leave a pending record unapproved. It must NOT affect the
  balance.
- B7: Sync SMS. Record counts only: created=N. Re-sync must give
  created=0 (dedup).
- B8: SMS Suggestions. Approving a suggestion creates the account; re-sync
  assigns transactions to it (counts only). Credit card and bank for the
  same bank must stay separate. Include K1/K2 investigation here.
- B9: Persistence. Force-stop (adb shell am force-stop com.tracker),
  relaunch. All accounts, records, and statuses must survive.

C. Input validation and money edge cases (use synthetic data)
- Amounts: 0, negative, empty, "abc", 0.01, 0.005, 12.345, 99999999.99,
  leading zeros, pasted "1,234.50".
  Expected: rejected or correctly rounded. No floating-point drift.
  Balance math must stay exact; values are stored as integer paise.
- Merchant: empty, 1 char, 200+ chars, emoji, Hindi/Arabic text. Check for
  truncation and layout breakage.
- Add Record with zero accounts. Expected: a clear block or guidance, no
  crash.
- Double-tap Save quickly. Expected: no duplicate record.
- Back button mid-form. Expected: no partial save; confirm discard if
  implemented.

D. Android platform behaviour
- READ_SMS permission:
  - Deny → Sync shows a clear message, no crash.
  - Deny with "don't ask again" → guidance to settings.
  - Grant → works.
  - Revoke in Settings while the app is backgrounded
    (adb shell pm revoke com.tracker android.permission.READ_SMS), then
    return → no crash.
- Lifecycle: background mid-form, return → state handled. Rotate if
  rotation is supported. Open the app while Metro is stopped (debug) and
  record the behaviour.
- Process death: enable "Don't keep activities" or kill via adb while on a
  detail screen, then reopen → no crash.
- Gesture-nav inset: check whether Save/Edit/Delete buttons sit in the
  bottom ~100px gesture zone. This is a known issue from Phase 2; confirm
  fixed or still present.
- Onboarding: shows on first launch only. This test requires an uninstall,
  so it belongs in section F.

E. Non-functional
- Cold start: adb shell am start -W -n com.tracker/.MainActivity (record
  TotalTime, 3 runs, median).
- Jank: adb shell dumpsys gfxinfo com.tracker reset, scroll Transactions
  for 10s, then dumpsys gfxinfo com.tracker. Record janky-frame % only.
- Memory: adb shell dumpsys meminfo com.tracker | grep TOTAL
- Accessibility:
  - Font scale: adb shell settings put system font_scale 1.3. Check
    clipping on every screen, then restore to 1.0.
  - Every button has a content description (filtered dump: grep
    content-desc on the specific element only).
  - Touch targets ≥ 48dp.
- Stability: across the whole run, grep logcat for FATAL EXCEPTION,
  "AndroidRuntime: FATAL", "Maximum update depth", ReactNativeJS errors,
  and process-died. Report COUNTS only.
